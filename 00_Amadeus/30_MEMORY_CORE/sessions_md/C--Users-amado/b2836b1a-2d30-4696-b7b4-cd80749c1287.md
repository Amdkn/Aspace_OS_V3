**Point clé** : un PowerShell à l'invite ne consomme rien. Un Claude "idle" continue de peser ~300 MB + enfants, parce qu'il maintient des connexions vivantes et un contexte en RAM.

## Pourquoi 30 terminaux → 100 % CPU

Ce n'est pas le CPU qui sature en premier, c'est la **RAM**. Mécanique :

| Poste | Valeur |
|---|---|
| RAM totale | 32 GB |
| RAM déjà utilisée avant les terminaux | ~14 GB (Windows + apps) |
| Coût par session Claude | ~300 MB |
| 30 sessions Claude | +9 GB |
| RAM disponible restante | ~9 GB |
| Seuil de paging Windows | ~85 % utilisé |
| 22.9/31.8 GB (72 %) mesuré | proche du seuil |

Quand la RAM sature, Windows **swap** sur le disque SSD. Le swap disque ↔ RAM est 1000× plus lent que la RAM. Le CPU monte à 100 % parce qu'il passe son temps à gérer les défauts de page, pas parce qu'il "travaille".

## Pourquoi pas de système actif/inactif

Windows Terminal ne suspend pas les onglets, et c'est volontaire : un terminal est un **shell stateful POSIX**. Le modèle mental est "ce que tu tapes est exécuté immédiatement, ce qui tourne continue". Microsoft a ajouté les onglets et les split panes, mais pas l'hibernation, parce que ça casserait les processus lancés en arrière-plan (builds, watchers, jobs).

Pour Claude, l'**état** est sur disque (le `.jsonl` dans `~/.claude/projects/`), mais le **runtime** (le `node.exe` + ses enfants) meurt avec le terminal. Pas de "suspend to disk" comme les onglets de navigateur.

## Ce qui existe comme approximation

1. **WSL + tmux** — détache une session, le process peut être tué, l'état survit. Propre, demande un setup WSL.
2. **Ctrl-C deux fois dans Claude** — interrompt la requête en cours, garde la session active mais inerte.
3. **`/exit` dans Claude** — termine proprement, écrit l'historique.
4. **Fermer le terminal** — perd le process, garde l'historique sur disque.
