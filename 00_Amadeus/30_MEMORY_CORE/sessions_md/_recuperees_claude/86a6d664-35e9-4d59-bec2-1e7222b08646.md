## Le défaut

`resolveIdentity()` (`identity.ts:91`) accepte l'identité que l'appelant
déclare. `resolveIdentityWithMembership()` (`identity.ts:204`) existe pour
vérifier cette déclaration contre la table `memberships` — mais **elle n'est
jamais appelée**. `setMembershipLookup()` (`identity.ts:187`) est exportée et
personne ne l'invoque.

Conséquence mesurée :

- `cli.ts` accepte `--role owner` sans aucune authentification ;
- le serveur MCP accepte un `__role: "owner"` forgé dans le JSON-RPC ;
- la route REST fait de même.

Toute la matrice de permissions (`permissions.ts`) repose sur ce rôle. Si le
rôle est déclaré par l'appelant, `assertPermission` ne protège rien : il vérifie
une affirmation contre elle-même.

## Ce qu'on attend

### 1. Brancher la vérification d'adhésion

Câble `resolveIdentityWithMembership` dans les trois adaptateurs. Le squelette
est déjà écrit (`identity.ts:204-242`) — lis-le avant de le réécrire.

Il lui faut une fonction de consultation, à injecter par `setMembershipLookup`,
de la forme `(userId, tenantId) => Promise<MembershipRole | null>`.

**La base est désormais alignée** : la table `public.memberships` porte
`user_id`, `tenant_id`, `role`, `status` (migration du 2026-08-17). Une adhésion
ne compte que si `status = 'active'`. Les rôles valides sont `owner`, `admin`,
`member`, `guest`.

Tu n'as **pas** le droit de modifier `src/lib/supabase.ts` (hors périmètre).
Si tu as besoin du client Supabase, importe-le — ne le réécris pas.

### 2. Le rôle déclaré ne fait plus autorité

Le rôle **effectif** doit venir de la consultation, jamais de l'entrée. Si
l'appelant déclare `owner` et que la table dit `member`, c'est `member` qui
s'applique. Si la table ne rend rien, l'appel est **refusé** — pas rétrogradé
en `guest` silencieusement : refusé, avec un message qui dit pourquoi.

### 3. Échouer fermé

Si la consultation d'adhésion n'est pas configurée (`setMembershipLookup`
jamais appelée) ou si elle échoue (réseau, base absente), l'appel doit être
**refusé** en production.

Il existe un mode démo légitime dans ce dépôt (`resolveIdentity` a une branche
`'demo'`). Ne le casse pas : le mode démo peut rester permissif, mais il doit
être **explicite** et impossible à déclencher depuis une entrée réseau. Lis
comment le reste du code distingue démo et production avant de trancher, et
explique ton choix dans le rapport.

### 4. `assertMembershipRolePresent`

Cette fonction existe et n'est jamais câblée non plus. Détermine si elle doit
l'être ici, ou si `resolveIdentityWithMembership` la rend inutile. Dis-le.
