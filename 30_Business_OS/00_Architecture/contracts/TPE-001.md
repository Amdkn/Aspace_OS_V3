## 1. Canonical Terminology

To avoid semantic collapse, the following concepts are strictly separated:

- **Identity**: The authenticated human or machine principal (who is making the request).
- **Membership**: The fact that an Identity belongs to an Organization.
- **Organization**: The legal/billing entity owning the resources.
- **Tenant**: The active isolated operational space (what data is being accessed). A single Organization may have multiple Tenants.
- **Role**: A static collection of Scopes assigned to a Membership.
- **Scope**: A bounded right to attempt a Capability (e.g., `case.progress.read`).
- **Policy**: The dynamic rules evaluating ProductContext, Tenant, Role, and Entitlement to reach a decision (ALLOW/DENY/REQUIRE_APPROVAL).
- **Subscription**: The commercial agreement to pay for a package.
- **Entitlement**: The materialized feature matrix and plan limits granted by the Subscription.
- **Infrastructure Ownership Model**: Cloud (Shared Supabase), Dedicated (Dedicated Supabase), or Sovereign (Self-hosted).

## 2. Invariants

- **Packaging Invariant**: Cloud, Dedicated, and Sovereign are profiles of the *same* product contracts, not three separate codebases.
- **Isolation Invariant**: A capability request must never cross tenant boundaries unless explicitly authorized by a cross-tenant policy.
- **Evaluation Invariant**: The identical capability request can be `ALLOW`, `DENY`, or `REQUIRE_APPROVAL` based solely on the tuple of `(ProductContext, Tenant, Role, Entitlement)`.
- **Traceability Invariant**: Every policy decision must yield a traceable reason for the outcome.

## 3. Authority Boundaries

- **Authentication Middleware**: Verifies Identity and establishes the principal.
- **Tenant Supervisor / Hydration**: Resolves the active Tenant context from the request and Membership.
- **Policy Engine (IAM)**: Evaluates Role, Scopes, and Capability permissions against Entitlements.
- **Data Access Layer (RLS)**: Enforces Tenant isolation expectations at the infrastructure level (e.g., Supabase RLS).

## 4. Inputs / Outputs

**Inputs (Policy Request):**
- Principal (Identity + Membership)
- Target Tenant Context
- Target Capability (e.g., `document.request.create`)
- ProductContext (Infrastructure Profile, current limits)

**Outputs (Policy Decision):**
- Status: `ALLOW` | `DENY` | `REQUIRE_APPROVAL`
- Traceable Policy Reason
- Bound Context (e.g., injected tenant_id for RLS)

## 5. State Ownership

- **Identity State**: Owned by the authentication provider.
- **Organization / Tenant State**: Owned by the canonical Operations repository (`OMK-DESKTOP-WEB-OS`).
- **Entitlement State**: Owned by the Billing/Subscription bounded context.

## 6. Commands / Queries / Events

**Queries:**
- `tenant.context.read`: Hydrates active tenant state.
- `policy.evaluate.read`: Asks if a principal can perform an action.
- `entitlement.matrix.read`: Fetches available features and limits.

**Commands:**
- `organization.member.invite`: Invites an identity.
- `role.scope.grant`: Modifies permissions.
- `infrastructure.ownership.transfer`: Shifts profile (e.g., Cloud to Dedicated).

**Events:**
- `tenant.hydrated`
- `policy.evaluation.failed`
- `entitlement.limit.exceeded`

## 7. Effects and Receipts

Policy enforcement must produce audit obligations.
External mutation completion requires an `EffectReceipt`.

For authorization failures, the receipt must include:
- `operation_id`
- `capability_id`
- `status`: `FAILED` (Authorization Denied)
- `policy_reason`

## 8. Failure / UNKNOWN Behavior

- If the active tenant context cannot be resolved, fail closed (`DENY`).
- If entitlement checks time out, fail closed (`DENY` or `UNKNOWN` requiring retry).
- UNKNOWN ≠ FAILED. An UNKNOWN authorization state must not default to ALLOW.

## 9. Migration and Versioning

This contract establishes the V1 baseline for TPE. Any previous loose coupling of user to workspace is superseded by the strict Organization -> Membership -> Tenant hierarchy.

## 10. Implementation Consumers

- `omk-services/OMK-DESKTOP-WEB-OS` (Canonical operations repo)
- Business OS Factory (Control plane compiling tenant configurations)

## 11. Contract Tests

Contract tests must prove:
- The same user in Tenant A cannot read Tenant B's data (Isolation).
- Exceeding a plan limit results in a traceable `DENY` (Entitlement).
- A user lacking a specific scope receives a `DENY` (Role/Scope).
- A sensitive capability returns `REQUIRE_APPROVAL` when configured.

## 12. Release Evidence

The contract is `VERIFIED` when:
- Authenticated membership properly leads to active tenant hydration (#289).
- Launch Cohort provisioning and RLS/tenant isolation proofs are demonstrated (#290).
- Real authenticated tenant isolation and restart/switch behavior pass in the canonical operations repo.
