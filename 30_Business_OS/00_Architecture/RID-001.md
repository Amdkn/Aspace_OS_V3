# A-SPEC-RID-001: Runtime, integration adapters, deployment profiles & contract release

## 1. Canonical terminology

- **Adapter plane:** The boundaries where external systems sit behind the business capabilities. External systems are integrated via strictly bounded adapters rather than leaking their implementations into core code.
- **DeploymentProfiles:** The context-aware environments where capabilities are executed and hosted, explicitly defining the infrastructural scope.
- **Contract gates:** Formal validation checkpoints ensuring regressions do not propagate, covering DB compatibility, tenant isolation, mobile reconnection, API schemas, etc.
- **Observability:** Correlation continuity from start of business process (e.g. Lead/Booking) all the way to fulfillment (EffectReceipt).

## 2. Invariants

- External systems must remain strictly behind business capabilities (adapters like PaymentProvider, CalendarProvider, etc.).
- The execution of a capability must preserve end-to-end correlation across boundaries.
- The release canary is explicitly an **economic journey** and not merely a superficial `/health = 200` ping.
- Deployment environments must enforce isolation and strict adapter timeout/rollback logic.

## 3. Authority boundaries

- **CI/CD Pipeline:** Enforces Contract gates during deployment.
- **Runtime:** Manages capability routing to the correct DeploymentProfile.
- **System Admin / Ops:** Sets environment mapping (shared vs dedicated vs sovereign).

## 4. Inputs / outputs

- **Inputs:** Capability execution requests (Commands/Queries), configuration bundles for adapters (e.g. `PaymentProvider` keys), DeploymentProfile descriptors.
- **Outputs:** Execution artifacts, correlated logs, EffectReceipts confirming adapter fulfillment.

## 5. State ownership

- **Runtime State:** Owned by the designated DeploymentProfile.
- **Integration State:** Ephemeral within the context of the capability; permanently resolved into EffectReceipts.
- **Release State:** Owned by the release orchestrator/Canary execution mechanism.

## 6. Commands / queries / events

- **Events:**
  - `integration.adapter.timeout`
  - `deployment.health.failed`
  - `release.canary.succeeded`
  - `release.rollback.triggered`

## 7. Effects and receipts

- Any mutation routed via an adapter must produce a persistent `EffectReceipt`.
- Observability requires transaction traces capturing end-to-end context (lead -> diagnostic -> booking -> sale -> customer -> workspace -> case -> fulfillment).
- Duplicate payment protection ensures identical transaction requests return cached `EffectReceipt` without invoking the adapter again.

## 8. Failure / UNKNOWN behavior

- **Adapter Failure / Timeout:** Capabilities must trigger a formal failure response rather than indefinitely blocking.
- **Webhook Replay:** System must deterministically handle re-delivered external webhooks.
- **Mobile Reconnect:** Connection interruption must safely replay and reconcile pending client states.
- **Deployment Rollback:** A failed canary or failed provisioning triggers an automatic revert to the previous deterministic state.

## 9. Migration and versioning

- Schema modifications (API schema, DB migrations) are validated automatically as part of Contract gates.
- Semantic continuity is strictly enforced across version updates.
- Deprecations in Adapter APIs require a transition plan mapping to the new Provider format.

## 10. Implementation consumers

- Any capability requiring external fulfillment (Payment, GWS, Analytics).
- All multi-environment deployments mapping a tenant to an infrastructural footprint (shared vs dedicated).

## 11. Contract tests

- Webhook replay testing (idempotency checks).
- DB migration safety (non-destructive operations).
- Tenant/RLS isolation assurance.
- Duplicate payment interception.
- Mobile reconnect/re-sync validation.

## 12. Release evidence

- **Canary Success Criteria:** One real or production-like prospect reaches full fulfilled service, generating complete evidence trails (correlation ID spanning lead to fulfillment).
- **Resilience Proof:** Injecting recoverable failures (e.g., adapter timeout, DB timeout) must properly trigger rollback and compensation paths as designed. A simple `/health = 200` check is rejected.
