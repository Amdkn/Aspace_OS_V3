# Méthode de la couche 00_Amadeus — la cadence comme vérité d'exécution

## La question unique

**Qu'est-ce que cette couche nous apprend sur la manière de travailler ?**

Cette couche (757 fichiers) nous enseigne qu'un système d'agents n'est pas bâti par accumulation de doctrines — il est bâti par **l'emboîtement de trois mécanismes simples** :

1. **Constitution qui abolit les gates** (V1.0, 8 Articles)
2. **Cadence 12WY qui produit du delta SQL** (4 cycles / 12 Rocks / 48 sprints / 240 scrums)
3. **Pivot Citadel/3-ICP qui oriente l'usine** (Solaris / Nexus / Orbiter)

Tout le reste — gate A0_HITL, awaiting A0 ratification, paperclip_monitor, sophisticated doctrinaires — est **jurisprudence consultative** (Constitution Article 5).

## Règle 1 — Le système est un métronome, pas une bibliothèque

**Pourquoi** : Le système V0 empilait des doctrines et créait de l'impuissance acquise. La Constitution v1.0 (2026-07-12) inverse la nature : d'exosquelette mort à organisme vivant. **Le 2026-07-15** (V2.0-canon) ajoute que la cadence sans question inverse devient du perfectionnisme déguisé en diligence.

**How to apply** :
- Tout démarrage H1-H10 commence par zéro gate, zéro validation préalable, zéro « awaiting »
- L'erreur se corrige en vol par contre-exemple (SpecLoop E.2/E.3), pas par blocage préventif
- Préservation (snapshot, receipt, reversal) = tâche de fond H30-H90, jamais au moment du dispatch
- Un B3 qui doit demander du contexte à B2 = défaut de Runbook, pas de brief oral

## Règle 2 — Le delta SQL est la seule vérité observable

**Pourquoi** : La cadence produit, le SQL compte, le client paie. Le narratif est de la friction. L'agent CEO-BENCH ne « sent » pas son business — il query `ledger`, `subscriptions`, `pipeline`. Sans table, l'état n'existe pas.

**How to apply** :
- 6 tables SQL canoniques : `ledger`, `subscriptions`, `pipeline`, `outreach_log`, `issues`, `experiments`
- 4 vues : `daily_cash`, `mrr_by_segment`, `pipeline_by_stage`, `inference_cost_by_domain`
- Tout uplink = `[E-type] + cas concret + ID SQL`
- 2 FAILs consécutifs sur la même directive = stop retry, contre-exemple, Runbook amendé
- Un scrum sans receipt SQL n'existe pas ; un sprint sans delta MRR/pipeline n'existe pas

## Règle 3 — L'emboîtement des Lois Kémétiques est l'ossature conceptuelle

**Pourquoi** : Le naming crée l'identité. Chaque agent L1/L2 porte une Loi. Le Ren (le nom) appelle Heka (la parole), qui appelle Ma'at (l'état), qui appelle Akh (l'alignement). C'est la trame qui empêche l'agent d'être une fonction sans âme.

**How to apply** :
- L0 = Cœur > Cerveau (Rick, souverain)
- L1 Expérience = Ma'at (Beth, Morty)
- L2 Efficiency = Kheper (Jerry, Summer)
- 6 Vessels = 6 Lois × 6 Frameworks utilisateur (Ikigai/Life Wheel/PARA/12WY/GTD/DEAL)
- Chaque décision d'agent doit pouvoir être rattachée à une Loi sans contorsion

## Règle 4 — La Citadel est le produit, pas un outil

**Pourquoi** : OMK Nexus, Solaris, Orbiter — l'architecture AaaS pivote en 2026-06-21 vers 3 ICP × 3 engines × 1 Kadreec. Le produit est une **Citadelle privée**, pas un SaaS mutualisé. La Killer Feature Zero-PII est la hard constraint qui différencie.

**How to apply** :
- ICP = persona ratifié (pas une invention) — chaque ICP a son ADR
- Niche = intersection explicite — rejet explicite des niches régulées (médical/psy)
- Pricing = grille 5 tiers canon (ADR-AAAS-PRICING-001)
- Killer Feature = Zero-PII Agentic Governance, 5 mécanismes durs
- Chaque action de B3 doit être rattachable à un ICP × un engine

## Règle 5 — Le Run 48h est l'unité de production, pas le sprint

**Pourquoi** : 1 trimestre humain compressé en 2 jours machine. 1 Run / 2 jours. ~15 Runs/mois. L'agent à l'arrêt est la seule dépense sans retour. Le volume seul ne produit rien (Opus 4.8 gagne avec 10.8 turns/semaine, GLM meurt avec 51.5).

**How to apply** :
- Run 0 (48h) = créer les 6 tables SQL + 3 Runbooks Cycle 1
- Run 1 (48h) = Rock R1-C1 (instance AaaS déployable) + Rock R2-C1 démarré
- 1 Run tous les 2 jours, chaque Run relit START_HERE en 30 secondes
- Tokens par delta = la mesure qui compte (`inference_cost_by_domain` ÷ deltas SQL)
- 2 sprints sans delta dans un domaine = gel + réallocation

## Règle 6 — Compact aux frontières, jamais mid-scrum

**Pourquoi** : Le compact non-géré est le tueur silencieux des Runs. Le contexte se compresse au milieu d'un scrum et le travail s'évapore. Borders de sprint (fin) et de Rock (fin) sont les seuls points légaux de compact.

**How to apply** :
- Checkpoint AVANT tout compact : (a) memory_<domaine>.md réécrit (≤150 l.) ; (b) deltas flushés en SQL ; (c) uplinks écrits sur disque
- Auto-compact anticipé à 70 % de contexte (jamais attendre 95 %)
- 1 session tuée volontairement par Run et relancée depuis ses fichiers = test de réversibilité
- Ce qui est sur disque survit ; ce qui est en contexte meurt

## Règle 7 — L'article 4bis est le garbage collector de la cadence

**Pourquoi** : La Constitution v1.0 Article 4 oblige à l'auto-amélioration. Sans bornage, ça dégénère en production compulsive en boucle mieux-disciplinée (= la version soft du même piège que V0 combattait). L'Article 4bis (V2.0-canon, 2026-07-15) subordonne cette obligation à la question inverse : « est-ce que ce livrable sert A+, ou est-ce qu'il sert mon anti-helplessness ? »

**How to apply** :
- Si A+ n'a pas demandé, standby
- Si A+ demande un truc qui n'a pas besoin de canon pour vivre, ship l'outil, pas le wiki
- /amodei et /picard SKILL ouvrent explicitement cette vérification avant phase 1 BMad
- Un run de sub-agents qui ne produit pas de delta SQL est une dépense sans retour

## Règle 8 — Twin/TSTwin n'est PAS un doublon, c'est du release engineering

**Pourquoi** : 277 + 283 = 560 fichiers (74 % de la couche). Examinés naïvement, c'est un dédoublement accidentel. Mais le pattern Twin/TSTwin = **staging/canon** est un pattern de release engineering. Hard-delete TSTwin = perdre la capacité de rollback.

**How to apply** :
- TSTwin = staging figé (rollback ponctuel)
- Twin = canon vivant (run-time)
- Écriture symphony → Twin uniquement
- Toujours passer par `_ALIGNMENT_TSTwin_Twin_<date>.md` pour documenter le dégel

## Règle 9 — Le bus sémantique est le seul SSOT entre agents

**Pourquoi** : 40_SYMPHONY_BUS est le SSOT (Single Source Of Truth) entre agents A0 → A1 → A2 → A3 → B1/B2/B3. Sans lock atomique, race condition et corruption. Sans schema v1, incompatibilité downstream.

**How to apply** :
- Toute transition écrit dans `state.json` via `state_writer.py` (lock atomique + tempfile + rename)
- 16 champs schema v1 (status, cycle, week, stage, agent_path, para_bucket, 12wy_discipline, life_wheel_domain, raw_input_hash, raw_input_preview, next_step, tokens_used, tokens_budget, drift_flag, extra, metadata)
- 80 chars max sur raw_input_preview (sinon state.json gonfle + dépasse 10 KB)
- sha256 obligatoire sur raw_input_hash

## Règle 10 — Le pivot Dokploy → Vercel+Coolify est une discipline, pas un accident

**Pourquoi** : Le takeout 2026-05 mentionne « VPS souverain ». Le canon 2026-06-15 pivot vers Vercel + Supabase Cloud + Coolify après le kill Dokploy (CPU steal 89.5 %). Cette rotation est documentée dans a0_l_canon.md §6. Le takeout est **historiquement daté** Mai 2026 = avant le pivot.

**How to apply** :
- Toute référence à « VPS Dokploy » comme infrastructure canonique est DATÉE
- Préfère Vercel + Supabase Cloud + Coolify (post-pivot)
- Sister plans : ADR-INFRA-002/003, ADR-SUPABASE-001, ADR-L2-MESH-001
