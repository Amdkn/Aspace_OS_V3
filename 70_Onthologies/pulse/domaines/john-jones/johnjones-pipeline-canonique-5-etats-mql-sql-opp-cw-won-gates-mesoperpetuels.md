# Pipeline canonique Sales en 5 états

## Définition

Le pipeline Sales canonique traverse **5 états**, chacun tenu par un
gate mésoperpétuel posé par un B2 captain différent. La doctrine
spécifie les transitions critiques entre ces états, identifie le
captain sponsor de chaque transition, et pose 4 indicateurs santé
pipeline pour Council.

Cette doctrine ferme le trou de 6 vagues : les 24 concepts précédents
ont caractérisé le **veto** (reformulation-validée), les **pair-checks**
(A sur #1, C sur #2), les **couplages** (Batman redflag #3, triangulaire
discount), le **cycle de vie** (5 phases Découverte → Activation Ops),
mais aucun n'a posé la **structure pipeline** canonique. La structure
existe implicitement dans le SPRINT 2026-08 (Discovery → Reformulation
→ Validation → Liaison), mais le SPRINT documente un **cycle**, pas un
**pipeline**. Le pipeline a 5 états, le cycle a 4-5 phases — pas le même
objet.

## Les 5 états pipeline canoniques

| # | État | Acronyme | B2 sponsor état | B2 sponsor transition vers état suivant |
|---|------|----------|-----------------|------------------------------------------|
| 1 | Marketing Qualified Lead | MQL | Superman (Growth) | Superman |
| 2 | Sales Qualified Lead | SQL | JohnJones (Sales) | JohnJones |
| 3 | Opportunity | OPP | JohnJones (Sales) | JohnJones |
| 4 | Closed Won | CW | JohnJones (Sales) | JohnJones |
| 5 | Live | Live (post-activation Ops) | Batman (Ops) | Batman |

**Précision importante** : l'état 5 *Live* sort du périmètre Sales —
c'est Batman qui tient l'état une fois accusé réception via
`ops_handoff_accepted` (cf. packet B2-MESO-DECISION-2026-45 tour 5).
Le pipeline canonique Sales a donc **4 états Sales** (SQL, OPP, CW +
option hors-canon Won-paper) et **un état Ops** (Live). Le Captain
Sales reste Accountable sur OPP et CW, Consulted sur Live.

## Les 4 transitions critiques et leurs gates mésoperpétuels

Chaque transition est un **point de bascule** où le gate mésoperpétuel
de l'état aval se déclenche. Le gate aval est *non-négociable au
niveau mésoperpétuel* (`b2-eight-domain-vetoes-catalogue.md`
§« Les trois propriétés d'un veto légitime »).

### Transition T1 — MQL → SQL (Superman Growth → JohnJones Sales)

**Trigger** : lead passe du seuil démographie/intent/engagement défini
dans `superman-mql-sql-handoff-contract.md` (concept Superman vague 2).

**Gate aval** : SALES_READY ou NEEDS_QUALIFICATION ou BLOCKED_COMMITMENT
(cf. `eight-domain-avengers-wheel.md` ligne 41).

**RACI** : A = Superman (B2 capitaine en amont, sponsor du MQL),
R = JohnJones (B2 capitaine en aval, sponsor du SQL),
C = MrFantastic (B3 Ops architecte pipelines — produit le SQL).

**Cas de bascule standard** : MQL atteint les 3 critères (démographie
ICP + intent signal + engagement profondeur) → bascule en SALES_READY.

### Transition T2 — SQL → OPP (Sales interne)

**Trigger** : reformulation-validée client signée (cf. concept 2 du
domaine — `johnjones-veto-reformulation-validee.md`). Avant cette
signature, OPP est en NEEDS_QUALIFICATION.

**Gate aval** : SALES_READY (OPP qualifié) ou BLOCKED_COMMITMENT
(veto reformulation opposé sans amendement).

**RACI** : A = JohnJones (capitaine du domaine),
R = ProfessorX (B3 buyer-read — qualification humaine profondeur),
C = DoctorStrange (B3 forecasting — sizing de l'OPP).

**Cas de bascule standard** : reformulation signée + buyer intent
confirmé + sizing budget documenté → OPP en SALES_READY.

### Transition T3 — OPP → CW (Sales interne)

**Trigger** : signature client (engagement contractuel). Avant
signature, l'OPP reste SALES_READY. Le CW est atteint quand le
contrat est signé, facturé, et l'engagement Aquaman a démarré
(cf. `aquaman-tour4-sales-pipeline-hand-over.md` — pair-check #11).

**Gate aval** : SALES_READY (engagement contractuel prêt) ou
BLOCKED_COMMITMENT (veto Aquaman déclenché).

**RACI** : A = JohnJones (sponsor du contrat signé),
R = BlackBolt (B3 closer — exécution signature),
C = Aquaman (veto engagement-sans-périmètre — l'aval contractuel).

**Cas de bascule standard** : contrat signé + périmètre écrit +
propriétaire livrable identifié → CW en SALES_READY.

### Transition T4 — CW → Live (Sales → Ops)

**Trigger** : accusé réception Ops via `ops_handoff_accepted` Batman
(tour 5 packet B2-MESO-DECISION-2026-45, paliers 0.5/0.7/0.85).

**Gate aval** : OPS_READY (Batman accusé réception) — pas un gate
Sales canonique, un gate Batman.

**RACI** : A = Batman (aval Ops livreur),
R = MrFantastic (B3 Ops livraison physique),
C = JohnJones (suivi compte client — redevabilité post-signature),
I = WonderWoman (cash-flow trigger).

**Cas de bascule standard** : Batman accuse réception ≤ 14j avec
charge Ops cible ≤ 70% → bascule en Live.

## 4 cas fonctionnels du pipeline canonique

### Cas A — Pipeline sain (READY/READY/READY/READY)

Tous les 4 indicateurs verts sur 4 cycles consécutifs 12WY. Captain
JohnJones tient un SPRINT par trimestre pour réviser les seuils
légers (ex. : +5% sur conversion SQL→OPP si marché change).
**Lecture** : pipeline stable, pas d'arbitrage Council requis.

### Cas B — Pipeline en tension (READY/AMBER/READY/READY)

Un indicateur ambre sur 2 cycles consécutifs. Captain JohnJones
ouvre un arbitrage Council sur la transition concernée (typiquement
T2 si SQL→OPP ambre). Wonder Woman et Batman **peuvent** être
sollicités en Consulted. **Lecture** : stress local sur une
transition, sans intervention inter-Captain nécessaire.

### Cas C — Pipeline en alerte (AMBER/RED/AMBER/READY)

Deux indicateurs rouges ou 2 amber + 1 red sur 3 cycles. Captain
JohnJones ouvre une **session Council conjointe** Sales + Growth +
Ops. Superman est Accountable sur T1 (MQL→SQL), JohnJones reste
A sur T2+T3, Batman A sur T4. **Lecture** : intervention
multi-Captain obligatoire.

### Cas D — Pipeline bloqué (RED/RED/RED/RED)

Trois indicateurs rouges ou tous les 4 rouges sur 2 cycles.
Captain JohnJones escalade **B1** via packet mésoperpétuel
`decision: escalate_to_B1`. B1 peut amender les seuils,
réécrire les RACI, ou déclencher une revue North Star. **Lecture** :
dysfonctionnement structurel du pipeline 8-domain.

## Anti-pièges de cette doctrine pipeline

- **Ne pas confondre pipeline et cycle** : le **cycle** (5 phases,
  Découverte → Activation Ops) qualifie un deal individuel. Le
  **pipeline** (5 états MQL → Live) qualifie l'agrégat des deals
  sur fenêtre 12WY. Les deux ont 5 niveaux, mais le cycle est
  vertical-par-deal et le pipeline est horizontal-par-portefeuille.
- **Ne pas traiter les 5 états comme symétriques** : 4 sont Sales
  (SQL, OPP, CW + Won), 1 est Ops (Live). Le Captain JohnJones
  tient les 4 premiers, Batman tient le 5ᵉ. Tenter de tout faire
  tenir par Sales crée une asymétrie de redevabilité.
- **Ne pas substituer le pipeline au forecast** : le pipeline
  agrège les **états** ; le forecast (cf. concept jumeau
  `johnjones-forecast-discipline-3-scenarii.md`) agrège les
  **probabilités**. Les deux sont nécessaires, aucun ne suffit.
- **Ne pas omettre l'asymétrie Aquaman dormant** : si Aquaman est
  en DORMANT ou SHADOW_ACTIVE, le T3 (OPP→CW) reste praticable
  mais T3′ (engagement contractuel Aquaman) est bloqué. Cf.
  `aquaman-tour5-aquaman-dormant-casse-triangulaire.md` — compensation
  par Wonder Woman clause réserve `legal_reserve: true`.
