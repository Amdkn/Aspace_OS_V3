# JohnJones — extension table 8×4 → 8×5 avec 5ᵉ état « forçage zéro » Sales

## Pourquoi ce packet maintenant

L'ouverture tour 4 R6 était : *« La table 8×4 NEEDS_SIGNAL Superman
doit être étendue pour « forçage zéro » Sales »*. JohnJones tour 4
(concept 5) avait posé la doctrine « forçage zéro » comme un 4ᵉ état
Sales, distinct de Aquaman dormant, Superman NEEDS_SIGNAL, et Batman
Ops procedure-dormant. Mais la table 8×4 est posée **par Superman**,
pas par les 7 autres Captains. Sales « forçage zéro » n'avait pas
été ajouté à la table.

C'est un **trou systémique** de la table Superman : un arbitrage
Council qui s'appuie sur la table 8×4 ne capture pas l'état « forçage
zéro » Sales. Le présent packet propose l'extension en **packet
mésoperpétuel Council-ready** soumis par JohnJones avec cosignature
Superman (auteur de la table 8×4).

**Procédure 5/8** (vs unanimité 8/8) — c'est une **extension**, pas
une **création**. La doctrine 8×4 existe déjà (`superman-needs-signal-vs-dormant-8domain-doctrine.md`),
ajouter un 5ᵉ état est une **adjonction**, pas une réécriture. Batman
tour 5 §« réfutation 4 » sur la procédure 6 étapes note qu'une procédure
rapide peut être choisie pour les **amendements mineurs** (5/8 au lieu
de 8/8) — sans sacrifier la ratification B1.

**Saisissabilité** sous 3 conditions cumulatives :

1. **Co-signature Superman** (auteur de la table 8×4). Superman tour
   3 a posé la doctrine 8×4 sans projeter le 5ᵉ état. Superman doit
   explicitement **consentir** à l'extension.
2. **Adoption 5/8** : 5 Captains sur 8 votent l'extension. Le vote
   est consultatif (B1 ratifie).
3. **Preuve en cycle** : observation d'au moins 1 SPRINT B1 orienté
   client où Sales traverse le 5ᵉ état sans forcer la production
   (cible : 1 cas/120j).

## L'extension de table 8×4 → 8×5

Tableau proposé :

| Captain | READY | NEEDS_SIGNAL | BLOCKED | DORMANT | **NON_FORCED** (5ᵉ état) |
|---|---|---|---|---|---|
| Superman (Growth) | ✓ | ✓ | ✓ | ✓ | — |
| **JohnJones (Sales)** | ✓ | ✓ | ✓ | ✓ | **✓** |
| Flash (Product) | ✓ | ✓ | ✓ | ✓ | — |
| Batman (Ops) | ✓ | ✓ | ✓ | ✓ | — |
| Cyborg (IT) | ✓ | ✓ | ✓ | ✓ | — |
| Wonder Woman (Finance) | ✓ | ✓ | ✓ | ✓ | — |
| Green Lantern (People) | ✓ | ✓ | ✓ | ✓ | — |
| Aquaman (Legal) | ✓ | ✓ | ✓ | ✓ | — |

**Note 1** : la colonne `NON_FORCED` ne s'applique qu'à JohnJones.
**Note 2** : `NON_FORCED` est **orthogonal** à `DORMANT` — un Captain
peut être dormant **et** non-forced (par exemple Aquaman dormant par
doctrine). Mais JohnJones n'est pas dormant par doctrine, donc le
5ᵉ état est spécifique.

## Les 4 cas d'application (hérités concept 5 tour 4)

1. **Mois creux** — pas de discovery active, throughput = 0 sur 4
   sprints. Sales traverse `NON_FORCED` (pas un DORMANT, pas un
   NEEDS_SIGNAL).
2. **Rock B1 non orienté client** — B1 mandate IT (Batman) ou Finance
   (Wonder Woman). Sales n'a aucun MQL à transformer. `NON_FORCED`
   par absence d'input amont, pas par défaillance Sales.
3. **Prospect en validation lente 8 sem** — discovery en Phase 2,
   validation en attente. `NON_FORCED` (≠ BLOCKED — la validation
   est en cours, pas bloquée).
4. **Scope réorienté** — pivot B1 (par exemple US premium Q4 2026),
   Sales attend la nouvelle orientation. `NON_FORCED` (≠ READY —
   Sales n'est pas prêt, il attend).

## Les 3 cas d'abus (hérités concept 5 tour 4 + extension)

1. **Déclarer NON_FORCED pour éviter accountability** — Sales
   déclare 5ᵉ état pour échapper à la signature client. C'est
   **abus politique** (cf. `b2-eight-domain-vetoes-catalogue.md`
   §Anti-pièges). Le packet Council-ready doit documenter la
   **trace** (lecture SPRINTS.md + scrums.md) avant d'accepter
   NON_FORCED.
2. **Confondre NON_FORCED et absence** — Sales n'écrit rien dans
   SPRINTS.md pendant 4 sprints. C'est une **absence**, pas un
   NON_FORCED. La discipline E-Myth Manager (concept 1 tour 3)
   impose une trace même minimale.
3. **Étendre NON_FORCED aux 7 autres Captains** — asymétrie
   fondée sur la doctrine Aquaman (pas forcer un domaine) —
   Batman, Flash, etc. ne sont pas « non-forced » au même sens.
   L'extension **doit rester Sales-spécifique**.

## Le 5ᵉ état vs la doctrine Aquaman dormant

JohnJones tour 4 (concept 5) a posé 3 différences structurelles entre
NON_FORCED Sales et DORMANT Aquaman. Le packet Council-ready les
reproduit verbatim :

- **Catalogue Aquaman** (triplet 35) **vs Fait JohnJones** — Aquaman
  steward un catalogue explicite (l'engagement-sans-périmètre),
  JohnJones ne steward pas un catalogue (il observe un fait).
- **0 packet accompagné de `decision: dormant`** Aquaman **vs 0 packet
  seul** JohnJones — la dormance Aquaman est un acte Council-ready
  (le packet Council Council pose la dormance), la non-forced Sales
  est un **fait observé**, pas un acte Council.
- **Déclencheur client** Aquaman (triplet 36) **vs déclencheur B3
  pair** JohnJones (MQL Superman Growth) — Aquaman se réveille quand
  un client arrive, JohnJones se réveille quand un MQL arrive.

**Conclusion** : NON_FORCED est **structurellement distinct** de
DORMANT. L'extension 8×5 ne **crée** pas un 5ᵉ état Aquaman-bis.
Elle **complète** la table par symétrie (1 colonne optionnelle
Sales-spécifique).

## Ce que ce packet ne fait PAS

- **Ne modifie pas la table 8×4** — l'extension est **adjonction**,
  pas réécriture. Les 4 colonnes existantes restent canoniques.
- **Ne soumet pas la doctrine Aquaman dormant à amendement** — la
  doctrine Aquaman (triplet 35) reste intacte.
- **N'étend pas le 5ᵉ état aux 7 autres Captains** — le 5ᵉ état
  est Sales-spécifique (cf. cas d'abus 3).
- **N'oblige pas Superman à étendre sa propre table** — Superman
  reste libre de **ne pas** appliquer l'extension à sa table interne
  Growth 8×4. Le packet Council-ready **propose** l'extension.

## L'asymétrie avec Batman tour 5 « cas-rouge-radar »

Batman tour 5 (concept 5 `batman-cas-rouge-radar-8-domain-seuil-passage.md`)
pose 4 scenarios Batman rouge (procedure vide / revue manquée / red
flag #1 / escalation bloquée) avec seuil de bascule 2+ sur 4.
**L'asymétrie** : Batman pose un seuil de bascule **binaire** (rouge
ou pas rouge), JohnJones pose un 5ᵉ état **discret** (non-forced est
un état, pas un seuil). Les deux patterns sont compatibles — Batman
peut basculer en rouge pendant un NON_FORCED Sales (par exemple,
Batman détecte procédure-sans-condition pendant que Sales attend
signal client).

## Anti-pièges spécifiques

- **Vouloir étendre la table 8×4 à 8×8 (5 états × 8 Captains)**
  serait un **overreach**. Le 5ᵉ état est Sales-spécifique, pas
  généralisable. L'extension asymétrique (1 colonne optionnelle)
  est le maximum saisissable.
- **Procédure unanimité 8/8 + B1** au lieu de 5/8 + B1 — une
  procédure trop lourde bloque la saisissabilité. L'extension
  est une **adjonction**, pas une réécriture, elle mérite 5/8.
- **Confondre NON_FORCED et DORMANT** — abus 1 ci-dessus. La trace
  dans SPRINTS.md + scrums.md est l'élément discriminateur.
- **Saisir le packet sans cosignature Superman** — sans Superman,
  la table 8×4 reste la source canonique et l'extension reste une
  projection unilatérale JohnJones.
