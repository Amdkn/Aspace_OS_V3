# Flash test continuité 4D — promotion grille à instrument

## Le problème que cet instrument ferme

Le test continuité 4D a été posé en **grille de justification** (concept 1 vague 3) avec 4 dimensions (build / run / pivot / sunset) et 5 critères acceptance par dimension. Le rapport tour 5 (`RAPPORT_dom-flash.md` §5.2 ouverture 7) notait : *« 0 cas réel de test de continuité 4D exécuté — la doctrine valeur-d'artefact reste reconstruite. »*

Le concept 28 tour 5 a **appliqué** la grille à Scarlet Witch H90 (transposition agent opérationnel ↔ artefact logiciel), avec 4 verdicts par dimension. Mais la transposition ne suffit pas : sans instrument de mesure **standardisé**, la grille reste **subjective** (chaque squad lead l'interprète différemment).

**3 problèmes** que l'instrument de mesure corrige :

1. **Subjectivité d'évaluation** — la grille est ouverte, chaque agent peut cocher n'importe quel score. Sans seuil chiffré, **orange ≅ rouge ≅ vert** dans la pratique.
2. **Pas d'intégration DoD 3 stades** — la grille est posée séparément, pas reliée au DoD 3 stades (concept 21 vague 4). L'artefact passe le DoD sans passer le test 4D.
3. **Pas de pré-livraison Captain America** — Captain America (squad lead Avengers) doit relire chaque artefact ship-ready. Le test 4D automatisé réduit la revue manuelle.

Ce concept **ferme l'ouverture 7 vague 5** en transformant la grille en instrument de mesure **chiffré**, **intégré au DoD 3 stades**, et **exécuté en pré-livraison**.

## Le scoring 4D — 4 métriques par dimension

Chaque dimension reçoit un **score 0-4** selon 4 critères chiffrés :

### Dimension 1 — Build (0-4)

| Score | Critère chiffré |
|---|---|
| 0 | Aucune documentation build, dépendances implicites |
| 1 | Documentation minimale, dépendances identifiées partiellement |
| 2 | Build documenté, dépendances complètes, ≥1 mécanisme de reprise |
| 3 | Build documenté, dépendances complètes, ≥1 mécanisme de reprise + ≥1 test de régression |
| 4 | Build documenté, dépendances complètes, ≥1 mécanisme de reprise, ≥1 test de régression, IaC ou équivalent |

### Dimension 2 — Run (0-4)

| Score | Critère chiffré |
|---|---|
| 0 | Aucune procédure run, owner unique non documenté |
| 1 | Procédure run minimale, owner identifié |
| 2 | Run documenté, owner identifié, alerting de base |
| 3 | Run documenté, owner identifié, alerting + dashboard, runbook complet |
| 4 | Run documenté, owner identifié, alerting + dashboard, runbook complet, **pas de dépendance person-named** (veto Flash test) |

### Dimension 3 — Pivot (0-4)

| Score | Critère chiffré |
|---|---|
| 0 | Aucun chemin de pivot, refonte complète requise |
| 1 | Pivot identifié, coût estimé > 50% du build initial |
| 2 | Pivot identifié, coût estimé 25-50% du build initial |
| 3 | Pivot identifié, coût estimé < 25% du build initial, pas de dépendance person-named |
| 4 | Pivot documenté, abstract layer ou interface stable, swappable sans rewrite |

### Dimension 4 — Sunset (0-4)

| Score | Critère chiffré |
|---|---|
| 0 | Aucune procédure sunset, feature éternelle implicite |
| 1 | Sunset identifié mais non daté |
| 2 | Sunset identifié, daté, owner de la procédure défini |
| 3 | Sunset identifié, daté, owner défini, runbook de désactivation |
| 4 | Sunset identifié, daté, owner défini, runbook + clause contractuelle (si garantie client) + **pas de dépendance person-named** |

**Score agrégé 4D** = somme des 4 dimensions (0-16).

## Les 3 verdicts — GREEN / YELLOW / RED

| Score agrégé | Verdict | Conséquence |
|---|---|---|
| **14-16** | **GREEN** | Artefact ship-ready, pas de veto Flash |
| **10-13** | **YELLOW** | Artefact ship-ready **avec** clause de revue à 30j (captain sponsor) |
| **0-9** | **RED** | **Veto Flash opposable** (triplet 25), artefact bloqué jusqu'à amendement |

**Cas spécial dimension Run** : si la dimension Run a un score < 4 ET contient une dépendance person-named, **verdict RED automatique** (override du score agrégé). Le veto Flash est binaire sur la dépendance person-named, pas gradué.

**Cas spécial dimension Sunset** : si la dimension Sunset a un score < 2 ET l'artefact a une garantie client, **verdict RED automatique** (clause contractuelle manquante, Aquaman pair-check #8 Legal → Product).

## Intégration au DoD 3 stades

Le DoD 3 stades (concept 21 vague 4, packet B2-MESO-DECISION-2026-41) impose 19 critères chiffres : 7 build, 6 run, 6 sunset. L'instrument 4D **s'ajoute** aux 19 critères comme **critère 20** :

```
build_score_4d + run_score_4d + pivot_score_4d + sunset_score_4d
  >= 14 (GREEN) OU 10-13 (YELLOW)
```

**Modifications au packet B2-MESO-DECISION-2026-41** :
- Ajouter `preuve_4d` dans le proof_expected (item 5).
- Le RACI stade-dépendant (Batman A build / Flash A run / B1 A sunset) s'étend : **Flash A run + 4D** (le test 4D est Flash-owned, pas Batman).
- La lecture large par defaut (concept 21 vague 4) reste valide — l'instrument 4D est **toujours lecture large** sauf `lecture_stricte_exception` activée.

## Exécution en pré-livraison par Captain America

Captain America (squad lead Avengers, concept 22 vague 4) **exécute** le test 4D sur chaque artefact ship-ready, **avant** livraison à Flash. La procédure Captain America :

1. **T-2 jours avant livraison** — Captain America reçoit la fiche ship-ready +评分模板 4D.
2. **T-1 jour** — Captain America passe les 4 dimensions, attribue les 4 scores (0-4).
3. **T-0** — Captain America **refuse** la livraison si verdict RED, **accepte** si GREEN, **accepte avec clause** si YELLOW.
4. **Section scrums.md** — Captain America consigne le score 4D dans la section `pre-livraison`.

**Coût** : ~30 min par artefact, Captain America est captain squad lead donc déjà impliqué.

**Bénéfice** : le veto Flash est **opéré avant la livraison**, pas après. La discussion « est-ce que cette feature viole le triplet 25 ? » est tranchée par le score, pas par une revue Council.

## Anti-pièges identifiés

1. **Confondre instrument 4D et DoD 3 stades**. L'instrument 4D est **un méta-outil** qui s'applique **au** DoD 3 stades, pas qui le remplace. Un artefact qui passe le 4D peut échouer le DoD, et inversement.
2. **Veto Flash binaire sur score agrégé**. Si le score agrégé est YELLOW (10-13) sans dépendance person-named, **pas de veto Flash**. Le veto reste **catégoriel** (triplet 25 + `b2-eight-domain-vetoes-catalogue.md` §3), pas gradué.
3. **Override systématique sur Run**. Si Captain America override un score Run = 4 sans dépendance person-named, il **introduit un faux RED**. Le test 4D est objectif, pas éditorial.
4. **Ignorer la dimension Pivot**. La dimension Pivot (coût de refonte) est souvent minimisée. Si Pivot = 0, l'artefact est **verrouillé** sur la solution actuelle — la roue doit pouvoir tourner.
5. **Sunset sans clause contractuelle**. La dimension Sunset note explicitement la clause contractuelle pour garantie client. Sans clause, Aquaman pair-check #8 (Legal → Product) peut opposer son veto (cf. `b2-eight-domain-vetoes-catalogue.md` §8 : « bloque toute prestation démarrée sans accord écrit sur le périmètre et la propriété du livrable »).
