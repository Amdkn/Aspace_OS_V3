# /project-init

Create a safe, reviewable ECC onboarding plan for the current project. This command should start in dry-run mode and only write files after explicit user approval.

## Usage

```text
/project-init
/project-init --dry-run
/project-init --target claude
/project-init --target cursor
/project-init --skills continuous-learning-v2,security-review
/project-init --config ecc-install.json
```

## Safety Rules

1. Default to dry-run. Do not modify `CLAUDE.md`, settings files, rules, skills, or install state until the user approves the concrete plan.
2. Preserve existing project guidance. If `CLAUDE.md`, `.claude/settings.local.json`, `.cursor/`, `.codex/`, `.gemini/`, `.opencode/`, `.codebuddy/`, `.joycode/`, or `.qwen/` already exists, inspect it and propose a merge/append plan instead of overwriting.
3. Use ECC's installer and manifest tooling. Do not hand-copy files or clone arbitrary remotes as an install shortcut.
4. Keep permissions narrow. Any generated settings should match detected build/test/lint tools and avoid broad shell access.
5. Report exactly what would change before applying anything.

## Detection Inputs

Read the current project root and detect stack signals from:

- package manager files: `package.json`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lockb`
- language manifests: `pyproject.toml`, `requirements.txt`, `go.mod`, `Cargo.toml`, `pom.xml`, `build.gradle`, `build.gradle.kts`
- framework files: `next.config.*`, `vite.config.*`, `tailwind.config.*`, `Dockerfile`, `docker-compose.yml`
- ECC config: `ecc-install.json`
- optional stack map: `config/project-stack-mappings.json` in the ECC repo

When the ECC checkout is available, use `config/project-stack-mappings.json` as the stack-to-rules/skills reference. If the file is unavailable, fall back to the installed ECC manifests and explicit user choices.

# Diagnostic : "Subprocess initialization did not complete within 60000ms"

## Ce que ça veut dire

L'extension Claude Code dans VS Code lance en arrière-plan un **sous-processus CLI** (le binaire `claude` qui fait le vrai travail). Au démarrage, ce sous-processus doit **s'initialiser en moins de 60 secondes** — bootstraper Node, lire ta config, tester l'auth, ouvrir la connexion API. S'il n'a pas confirmé "prêt" avant le timer, l'extension abandonne et te crache ce message.

Le suffixe "check authentication and network connectivity" est le diagnostic par défaut que l'extension te suggère, mais en vrai **6 causes** sont possibles.

## Les 6 causes probables (par fréquence)

### 1. **Authentification invalide/expirée** (cause #1 dans 70% des cas)
Ton runtime est **MiniMax-M3 via MiniMax** (cf. CLAUDE.md). L'extension cherche ces variables :
- `ANTHROPIC_API_KEY` 
- `ANTHROPIC_AUTH_TOKEN`
- `ANTHROPIC_BASE_URL` (doit être `https://api.minimax.io/anthropic`)

**Test rapide** : Ouvre un terminal VS Code et tape `echo $env:ANTHROPIC_BASE_URL` (PowerShell) ou `echo $ANTHROPIC_BASE_URL` (bash). Si vide ou faux → c'est ça.

### 2. **Subprocess CLI introuvable ou bloqué**
L'extension spawn `claude` (le CLI) en child process. Si :
- Le binaire n'est pas dans le PATH
- Une autre instance `claude` tourne déjà (verrou de port/fichier)
- Defender/Antivirus a killé le process au boot

**Test** : `claude --version` dans le terminal VS Code. Si ça retourne un version → CLI OK. Si "command not found" → reinstall l'extension ou ajoute le PATH.

### 3. **Connexion réseau bloquée vers MiniMax**
L'extension doit joindre `https://api.minimax.io/anthropic` au boot pour valider l'auth. Si :
- VPN activé mais pas de route vers MiniMax
- Proxy d'entreprise qui intercepte
- Firewall Windows bloque le child process (les subprocess Node héritent souvent de règles différentes du process parent)

**Test** : `curl https://api.minimax.io/v1/models -H "Authorization: Bearer $ANTHROPIC_API_KEY"` (ou `Invoke-WebRequest` en PowerShell). Si timeout → réseau.

### 4. **Resource exhaustion / port conflict**
Une instance VS Code zombie qui hold le lock du subprocess port. Solution : fermer **toutes** les fenêtres VS Code (pas juste recharger), puis rouvrir.

### 5. **Version VS Code trop vieille / extension corrompue**
L'extension Claude Code nécessite VS Code ≥ 1.85 (de mémoire). Et parfois le cache de l'extension se corrompt.

**Fix** : `Ctrl+Shift+P` → "Claude Code: Clear Extension Cache" ou réinstalle l'extension.

### 6. **Race condition au premier lancement**
Si tu viens d'ouvrir VS Code à froid, le subprocess peut juste avoir besoin de **plus de temps** que 60s la première fois (scan de workspace, indexation). Solution simple : attendre, puis réessayer. Si reproduit systématiquement → c'est un autre problème.

## Ordre de diagnostic (5 min max)

1. **View → Output → Claude Code** : les vrais logs du subprocess sont là. Cherche la dernière ligne avant le timeout — elle dit *exactement* où il a bloqué (auth check, network probe, ou spawn).
2. **Terminal VS Code** : `claude --version` puis `echo $env:ANTHROPIC_API_KEY` (et les 2 autres vars).
3. **Test API direct** : `curl https://api.minimax.io/v1/models` (sans auth, juste pour voir si ça résout).
4. **Kill switch** : Ferme tout VS Code → rouvre. Si toujours KO → réinstalle l'extension.

- Soit **MiniMax API key révoquée/expirée** (vérifie sur le dashboard MiniMax)
- Soit **le child process n'arrive pas à joindre `api.minimax.io`** (DNS, proxy, ou firewall hérité)
